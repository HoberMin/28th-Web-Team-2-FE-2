# 디자인 피드백 문서 규격

목적: 코드를 Figma에 맞추는 과정에서 드러난 디자이너의 실수를 찾아, 어느 노드의 무엇이 잘못됐는지 짚어준다.

형식 문서가 아니라 탐지 문서다. 형식은 그 결과를 담는 그릇일 뿐이고, 이 스킬의 값어치는 아래 탐지 체크리스트에 있다.

## 대원칙

- 코드를 Figma에 먼저 맞춘다. 이 문서는 "안 맞춘 변명"이 아니라 "맞춘 뒤 남은 질문"이다.
- 값을 임의로 조정하지 않는다. 대비가 나빠도 Figma 값 그대로 두고 문서에 적는다 (figma-bridge §3).
- 모든 항목은 어디가 문제인지부터 밝힌다. 대상 노드 링크 없이 토큰 이름만 적는 항목은 쓰지 않는다.
- 추측한 노드 id를 만들어내지 않는다. 노드를 모르면 화면 이름을 평문으로 적는다.
- 수치는 실제 계산값만 적는다. 어림값·추정 금지.

## 선별 기준 (탐지보다 먼저 — 찾은 걸 다 쓰지 않는다)

탐지 체크리스트를 돌리면 항목이 수십 개 나온다. 그걸 다 적으면 디자이너가 무엇부터 봐야 할지 알 수 없고, 진짜 막힌 항목이 사소한 것들 사이에 묻힌다. 문서에 넣기 전에 아래로 거른다.

먼저 한 줄로 가른다 — 규칙인가 내용인가

이 문서가 하는 일은 린트지 교정이 아니다. 린터가 변수명 규칙 위반은 잡고 주석 오탈자는 안 잡는 것과 같다. 판정은 한 질문으로 끝난다.

이 결함이 코드로 그대로 옮겨지는가

- 간격 3px → 누군가 p-[3px]로 옮긴다. 규칙이다
- 시스템 밖 폰트 → 타이포 토큰이 안 잡힌다. 규칙이다
- focus 상태 없음 → 옮길 게 없어 구현이 막힌다. 규칙이다
- 더미 금액의 쉼표 자리 → 실데이터로 대체된다. 내용이다, 적지 않는다

규칙 위반은 네 갈래다. 탐지 체크리스트를 이 갈래로 되읽으면 빠뜨리지 않는다.

- 스케일 이탈 — 4px 그리드 밖, 소수점 크기·좌표, 스케일에 없는 간격
- 토큰 미사용 — 시스템 색·폰트·radius·그림자 대신 임의값
- 상태·조합 누락 — focus·disabled·error·빈 화면, variant 조합 구멍
- 구조 위반 — 마스터에서 떼어냄, 오토레이아웃 아님, 자동생성 variant 이름. 코드로 옮기는 걸 물리적으로 막는 유형이라 가장 먼저 올린다

예외 하나. 더미인데도 넣어야 할 때가 있다. 그 더미가 규격을 가릴 때다. 세그먼트 세 칸 중 둘이 같은 문구면 세 번째 칸이 무엇인지 알 수 없어 구현을 못 한다. 쉼표 오타는 몰라도 되지만 이건 몰라선 안 된다. 판단 기준은 오타냐 아니냐가 아니라 그걸 모르고도 구현할 수 있느냐다.

그 다음 아래로 조인다

넣는다 — 셋 중 하나라도 해당할 때
- 안 고치면 구현이 막힌다. 토큰·규격이 없어서 코드가 추측해야 하는 상태
- 사용자에게 실제 피해가 간다. 글자가 안 읽히거나(4.5 미달) 버튼을 못 누르거나(44 미만) 내용이 잘린다
- 값이 서로 어긋나서 어느 쪽을 따를지 디자이너만 정할 수 있다

뺀다
- 렌더 결과가 같은 것. 중복 정의, 이름 취향, 계층 기준 — 지금 결정 안 해도 화면이 똑같다
- 오타·더미 텍스트·쉼표 자리·자릿수. 공유 페이지에 노출돼 남에게 보이는 경우가 아니면 적지 않는다
- 기준에 아슬아슬하게 걸친 것. 대비 4.45처럼 0.1 미만 차이는 실질 피해가 없다
- 우리가 코드에서 처리하면 끝나는 것. 디자이너에게 물을 일이 아니다
- 아직 화면이 없는 미래 대비. 그 화면을 만들 때 다시 올린다

뺀 것은 유형만 문서 머리말에 한 줄로 남긴다 — 예: 오타·더미 문구, 렌더 결과가 같은 이름 취향, 0.1 미만으로 걸친 대비는 뺐다. 다음 라운드에 조건이 바뀌면 그때 올린다.

뺀 항목을 따로 파일로 아카이브하지 않는다. 한 번 시도했다가 걷어냈다 — Figma가 5일 만에 규격 27개에서 85개로 늘어난 파일이라 px 실측값은 며칠이면 어긋나는데, 파일이 남아 있으면 다음 사람이 그걸 믿는다. 없는 것보다 나쁘다. 낡지 않는 건 뺀 유형이고 낡는 건 개별 수치다. "다시 안 재도 된다"는 이점도 어차피 성립하지 않는다.

한 문서에 항목이 10개를 넘으면 기준이 느슨해진 것이다. 다시 조인다.

다만 10은 신호지 상한이 아니다. "넣는다" 셋에 걸리는 걸 억지로 빼면 규격을 어기는 쪽이 된다. 실제로 85개 규격을 한 번에 훑은 회차에서 12개로 조였다가, 대비 1.11(선택된 행이 안 보임)·구조 위반·4px 그리드 이탈을 "너무 많아서" 잘라낸 게 리뷰에서 규격 위반으로 잡혔다. 20개가 넘으면 먼저 의심할 것은 기준이 아니라 대상 범위다 — 한 문서가 규격 85개를 담으려 한 게 아닌지 보고, 그렇다면 회차를 쪼갠다.

## 탐지 체크리스트

실수는 대부분 "두 곳을 대조했을 때"만 보인다. 한 곳만 보면 안 보인다.

값의 어긋남
- 같은 컴포넌트 안의 글자 색과 아이콘·에셋 fill이 실제로 같은 값인가. SVG를 열어 fill을 직접 읽는다. 코드가 범용 토큰으로 근사해 놓으면 화면상 멀쩡해 보여서 오래 안 보인다
- Variable 값 ↔ 컴포넌트 노드 실측 ↔ export된 에셋, 셋이 일치하는가
- 이름이 다른데 값이 같은 토큰이 있는가 (중복 정의 — 나중에 한쪽만 못 바꾼다)
- 같은 역할인데 값이 다른 것이 있는가 (그림자 크기, 같은 아이콘의 다른 px)

빠짐
- variant 조합 매트릭스에 빈칸이 있는가 (예: outlined × pressed)
- 상태 3종(로딩·에러·빈)과 포커스가 있는가. 실무에서 가장 많이 빠진다
- 코드가 쓰는데 세트에 없는 형태가 있는가 (화면에서만 쓰는 변형)

대비
- 텍스트 4.5, UI 요소·아이콘 3 기준으로 실제 계산한다
- 색에만 의존해 정보를 전달하는 곳이 있는가 (WCAG 1.4.1)

이름·구조
- 시맨틱 토큰에 컴포넌트명이 들어갔는가 (그 컴포넌트 밖에서 못 쓴다)
- 같은 부모 아래 하위 축 기준이 갈렸는가 (한쪽은 색상, 한쪽은 용도)
- 같은 개념에 다른 속성명을 썼는가 (state vs status)
- 복붙 흔적이 있는가 (중복 접두사, wrapper 이름 미갱신)

잘림·터치
- 고정 크기 안에 들어가는 최대 문자열이 실제로 들어가는가 (순위 10위, 금액 자릿수, 긴 가게명)
- 터치 영역이 44 미만인가

잔재
- 더미 텍스트·오타·자릿수 오류가 공유 페이지에 남아 있는가
- 오토레이아웃 잔재(자식 1개인데 gap), 고정 높이 잔재

## 어디에 쓰는 규격인가 (auditor와 구분)

| | design-feedback (이 문서) | figma-handoff-auditor §출력 형식 |
|---|---|---|
| 대상 | 코드 ↔ Figma 비교 | Figma 파일 자체 |
| 언제 | 토큰 sync·컴포넌트 구현 후 | 핸드오프 전 파일 정리 |
| 저장 | 디자인_docs/feedback/ | 디자인_docs/audit/ |

두 규격은 별개다. 서로의 섹션 구성을 가져다 쓰지 않는다.

## 형식 (v1.md 구조 고정 — 임의로 바꾸지 않는다)

표기
- 볼드·백틱·코드블록·인용문·이모지 금지. 평문으로 쓴다
- 링크는 필수에 가깝다. 대상 노드로 바로 갈 수 있어야 한다
- 번호는 문서 전체에서 이어간다. 섹션마다 1로 되돌리지 않는다

표 컬럼 (고정 4칸 + 번호). 마지막 칸 헤더 문구만 섹션에 맞게 바꿔 쓴다

```
| # | 대상 | 어디에서 | 현상태 | → 의도 확인 |
|:--:|---|---|---|---|
| 1 | [노드 이름](Figma URL) | 이게 보이는 화면·컴포넌트 | 지금 상태를 짧게 | 무엇을 어떻게 할지 |
```

대상 칸에는 컴포넌트·토큰 이름을, 어디에서 칸에는 그게 실제로 노출되는 화면을 적는다. 디자이너가 "어느 화면을 열어 확인해야 하는지" 바로 알 수 있어야 한다.

두 칸 모두 딥링크를 건다. 대상은 컴포넌트 노드 또는 Variables 컬렉션으로, 어디에서는 화면 프레임 노드로. 항목을 줄이거나 옮길 때 링크가 같이 떨어져 나가기 쉬우니, 문서를 고친 뒤 링크 없는 행이 0인지 확인한다.

화면 노드 id를 모르면 디자인_docs/audit/ 의 전수조사 문서에서 찾는다. 화면 프레임 목록이 노드 id와 함께 정리돼 있다. 거기에도 없으면 평문으로 적고, 노드 id를 추측해서 만들어내지 않는다.

컴포넌트가 실제로 어느 화면에 나오는지는 코드에서 확인한다. 사용처를 grep해서 확인하지 않은 화면을 짐작으로 적지 않는다.

체크박스를 쓰고 싶으면 표 대신 목록으로 간다. GitHub 표 안의 체크박스는 눌리지 않는다. 다만 표를 버리면 대상·위치 컬럼이 산문에 묻히므로 기본은 표다.

항목이 5개 이하면 섹션을 나누지 않는다. 표 하나로 두고 제목을 "반드시 정해주셔야 하는 것"으로 쓴다. 항목 4개를 A~D로 쪼개면 분류가 내용보다 커진다.

섹션 순서 (항목이 많을 때만. 빈 섹션은 통째로 생략)

| 섹션 | 담는 것 |
|---|---|
| A. 오류로 보이는 것 | 틀렸다고 볼 근거가 있는 것 |
| B. 빠진 것 | 있어야 하는데 없는 규격·상태·토큰 |
| C. 대비 미달 | 코드는 Figma 값 그대로 두고 보고만 한다 |
| D. 이름·구조 | 네이밍·계층 기준이 갈린 것 |
| E. 잘림·터치 영역 | 고정 크기·최소 터치 영역 |
| F. 일관성 | 같은 역할인데 값이 다른 것 |
| 이미 코드가 피그마에 맞춘 것 | 액션 없음. 무엇이 바뀌었는지만 알림 |
| 아직 못 맞춘 것 | 맞출 토큰·규격이 없어 멈춘 것 |
| 이전 문서에서 이어받은 항목 | 아래 승계 규칙 |

헤더는 v1.md와 같은 형태로 쓴다.

```
# 디자인시스템 리뷰

[출처 이름](Figma URL) 실측 · YYYY-MM-DD
대상 이름을 누르면 피그마로 이동합니다. 위쪽일수록 오류에 가깝고, 아래로 갈수록 판단이 필요한 항목입니다.
```

## 승계 규칙

새 문서를 쓸 때 이전 피드백 문서의 미해결 항목을 훑고, 마지막 섹션에 표로 적는다.

| 이전 번호 | 상태 | 내용 |
|:--:|---|---|
| v1 73 | 해소됨 | 어떻게 확인했는지 |
| v1 19 | 그대로 | 아직 안 바뀜. 이번 문서 몇 번으로 다시 올렸는지 |
| v1 26 | 판단 필요 | 바뀌긴 했는데 해소인지 애매한 이유 |

이 섹션이 없으면 디자이너가 지난 지적이 반영된 건지 무시된 건지 알 수 없다. 이어받을 항목이 없어도 이전 문서 없음 한 줄은 남긴다.
