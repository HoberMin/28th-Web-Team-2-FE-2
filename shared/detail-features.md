## 0. 이번 라운드에서 바뀐 판단 (읽기 전 필수)

**① 가게 축을 신설했다 (가장 큰 변화)**
기존 27개 화면이 전부 **품목 축**이었다(감자 화면, 오이 화면…). 그런데 기획안 §1의 문제 정의는
`A가게 2,490원 / B가게 3,000원 / 대형마트 4,990원` — **가게를 비교하는 문제**다. 품목별 최저가만
알려주면 감자는 A가게, 오이는 B가게로 흩어져 발걸음이 늘고, 핵심 가치인 "노력 절약"과 반대가 된다.
→ 가게 상세(F09) · 싼 가게 랭킹 · 장보기 코스 · 단골 가게가 이 축에서 나왔다.

**② 품목을 9종 → 46종으로 맞췄다**
문서(`kamis-vegetable-data-spec.md`)는 46종인데 코드는 9종이었고, 그중 옥수수는 KAMIS에 없는
품목코드였다. 46종 규격을 그대로 반영하면서 규격의 "버그 수정" 항목(당근 232/01, 피망 255,
오이 개수 단위, 애호박·쥬키니 분리, 방울토마토 추가)도 함께 적용했다.

**③ 단위가 kg 고정이던 것을 품목별로 갈랐다**
46종의 기준 단위는 kg·g·개·포기 4종이다. kg 고정 표기는 **오이 3개를 "3kg"으로 보여주는 버그**를
만들고 있었다. 시장은 "1망 5,000원"처럼 팔기 때문에 시장 단위 → 기준 단위 환산도 함께 넣었다.

**④ 판단을 화면 밖으로 꺼냈다**
매장 가격표 앞에서 앱을 켜는데, 기존 경로는 홈 → 검색 → 품목 → 시세 화면 스크롤 4회였다.
가격만 입력하면 판정이 나오는 즉석 판단(F10)을 최단 경로로 신설하고, 판정 뒤 그 값이 그대로
제보로 넘어가게 이었다(제보 비용 ≈ 0).

**⑤ 디자인 시스템을 하나로 통일했다**
같은 화면 안에 Figma hex 직접 지정과 seed 토큰이 섞여 있었다(report-list 15곳, 시세 화면 12곳,
그래프 10곳). 전부 seed 토큰으로 정리했고, 손으로 복붙된 세그먼트 탭 3곳·토글·댓글 입력을
seed 정품 컴포넌트로 교체했다. 이 과정에서 **가격 알림 ON 배경이 존재하지 않는 토큰(`bg-brand`)을
써서 무색으로 보이던 버그**가 드러나 함께 고쳤다.

## 메인 기능

#### 공공 시세 조회(KAMIS)

정의: KAMIS 채소 데이터 규격 46종 기준으로 오늘 시세·평균가·기간별 추이를 제공한다.

해결하는 문제: 판단 기준선이 없어 감으로 사고파는 문제.

프로세스:
1. 품목·품종(kindCode)·등급(04 상품)으로 KAMIS 조회. 인증키 없으면 더미 시세로 폴백
2. 단위 정책 분기 — kg·g는 `p_convert_kg_yn=Y`, 개·포기는 `N`(소비자가 그 단위로 사는 품목)
3. 배추·무는 계절형 — 봄/여름고랭지/가을/월동 4개 품종을 **전부 조회해 응답 있는 것만 평균**(캘린더로 고정하지 않음)
4. 오늘 시세·평균가·기간별(1주/1개월/1년) 시리즈 반환
5. 비수기 품목(수박·참외·딸기·갓)은 데이터 없음이 정상 → 빈 상태로 표시

화면 요소: 시세 없는 품목은 홈 그리드에서 "여름 한정" 등 계절 문구로 대체. 데이터 에러 시 더미 폴백

렌더링·캐싱: 서버 전용(`_lib/kamis.ts`, `server-only`). `revalidate: 3600` + `tags: ["prices"]`.
홈·랭킹·장바구니는 라우트 세그먼트 `revalidate = 3600`

결정 필요:
- 46종 각각의 등급 코드가 실제로 맞는지 최종 검증
- 배추·무 계절 품종의 실제 kindCode 4개 값(규격 문서에 없어 지금은 01~04로 조회 시도 — `TODO(✍️)`)
- 방울토마토·대추방울토마토의 단위가 규격상 "개"인데 개당 가격이 수백 원대라 화면에서 어색함. 팩 단위가 맞는지 확인

#### 이웃 제보가

정의: 이웃이 사진 또는 직접 입력으로 올린 실제 목격 가격을 동네(동) 단위로 모아 보여준다.

해결하는 문제: 공공 시세가 시·도 단위까지만 나와 동네 가격을 알 수 없는 문제. 서비스의 유일한 차별점.

프로세스:
1. 제보 방식 선택(촬영/직접입력)
2. 가게 위치 선택(GPS+Kakao 검색, 미등록 시 직접입력)
3. 품목·양·가격 입력 — 양의 단위는 품목별(kg·g·개·포기). 촬영·즉석 판단에서 왔으면 프리필
4. 구매 여부 선택
5. 제출 → 제보 완료 화면 → 동네 제보가 목록에 반영

화면 요소:
- 제보 없는 동네는 빈 상태
- 목록은 3열 표(제보일 / 오늘 시세 기준 차이 / 가격)
- **시세 화면에서 그래프보다 위에 배치**(UX 3차 변경) — 이 서비스의 차별점이자 판단의 직접 근거이고, 공공 시세는 기준선일 뿐 동네에서 실제로 가능한 가격이 아니다
- 가게명을 누르면 가게 상세(F09)로 이동

결정 필요: 허위 제보 신고·제재 기준을 둘지(지금은 이상치 표시까지만)

#### 시세 그래프(기간 전환)

정의: 품목별 시세를 1주·1개월·1년 단위로 전환해 보여주는 그래프.

해결하는 문제: 판단 근거가 기억뿐이라는 문제. 과거 추이로 보완한다.

프로세스:
1. 기간 탭 선택(1주/1개월/1년)
2. 해당 기간 시리즈 조회
3. 그래프 렌더링, 포인트 터치 시 날짜별 가격 표시

화면 요소: 데이터 부족한 구간은 빈 구간으로 표시(끊긴 그래프와 구분되게)

결정 필요: 데이터 없는 구간을 시각적으로 어떻게 표현할지

#### 찜하기 + 야채 검색 + 그룹 필터

정의: 46종 중 관심 품목을 찜하거나, 이름으로 검색하거나, 종류별로 걸러 빠르게 찾는다.

해결하는 문제: 46종을 3열 그리드에 그대로 쏟으면 16줄이라 홈이 스크롤에 잠기는 문제.

프로세스:
1. 그리드에서 하트로 찜 토글, 검색창에 이름 입력, 또는 그룹 칩 선택
2. **검색어가 있으면 그룹 필터를 무시한다** — 이름을 아는 사람은 이미 목적지가 있고, 두 필터가 동시에 걸리면 결과가 왜 비었는지 알 수 없다

화면 요소: 그룹 칩 7종(감자·뿌리 / 잎채소 / 열매채소 / 고추 / 양념 / 버섯 / 과채) + "전체".
KAMIS 부류코드(100/200)는 값이 2개뿐이라 필터로 못 쓰므로 "장 볼 때 묶는 방식"으로 따로 나눴다.
찜·검색 결과 없을 때 각각 빈 상태

결정 필요: 이름 비슷한 품목(대파/쪽파, 적상추/청상추, 애호박/쥬키니) 구분 표시 방식

#### 즉석 판단(신호등) 🆕 F10

정의: 품목·단위·가격만 입력하면 우리 동네 기준으로 🟢사도 좋음 / 🟡적당함 / 🔴비쌈을 한 장으로 판정한다.

해결하는 문제: **사용자가 앱을 정말 켜는 순간은 매장 가격표 앞의 3초**인데, 기존 경로는
홈 → 검색 → 품목 선택 → 시세 화면 스크롤 4회였다. 판단까지 너무 멀다.

프로세스:
1. 홈 최상단 진입점 또는 시세 화면 "지금 본 가격이 괜찮은지 확인하기"로 진입
2. 품목 선택 — 찜한 야채 → 인기 8종 순 칩, 또는 검색
3. 파는 단위 선택(1kg / 1단 / 1망 / 1박스 등) → 기준 단위 환산은 앱이 한다
4. 가격 입력 → **입력 중 실시간 판정**
5. 판정 후 "이 가격 제보하기" → 가격·수량을 들고 제보 플로우로

판정 기준: 우리 동네 최저 제보가가 있으면 **그것을 기준**으로, 없으면 오늘 공공 시세.
("같은 동네에서 이 가격에 산 사람이 있다"가 더 강한 근거다) 기준 대비 ±8% 밖이면 싸다/비싸다

화면 요소:
- 판정 카드는 **결론 → 근거 → 다음 행동** 순서. 무엇과 비교했는지(기준가·제보 건수)를 밝힌다
- 색만으로 뜻을 전하지 않는다 — 문구가 결론을 그대로 말하고 스크린리더용 라벨을 따로 둔다
- 시세 데이터 없는 품목(비수기)은 판정 불가 → 제보 유도 문구
- 하단 CTA는 **항상 렌더**하고 비활성으로 둔다(조건부로 나타나면 판정 순간 화면이 위로 튄다)

결정 필요: ±8% 밴드가 적절한지 실사용으로 재조정. 품목별로 다르게 둘지

#### 가게 상세 🆕 F09

정의: 한 가게의 전 품목 제보가를 한 화면에 모아 "이 가게는 뭐가 싸고 뭐가 비싼가"에 답한다.

해결하는 문제: 모든 화면이 품목 축이라 **"오늘 어느 가게 갈까"에 답하는 화면이 없던** 문제.
기획안 §1의 문제 정의(가게 비교)에 정면으로 답하는 유일한 화면이다.

프로세스:
1. 랭킹 "싼 가게" 탭 / 시세 화면 제보 목록의 가게명 / 홈 단골집 카드에서 진입
2. 제보를 place로 묶고, 같은 품목은 **가장 최신 1건**을 대표로 채택(가격은 시간에 민감)
3. 시세 대비 싼 품목 순으로 정렬 — 이 가게에 갈 이유가 먼저 읽혀야 한다
4. 앱바 우측 북마크로 단골 등록

화면 요소:
- 요약 한 줄("제보 N개 품목 · M개가 시세보다 싸요 · 최근 제보 O일 전")
- 품목 행마다 제보 신선도, 교차 검증 배지, 이상치 "확인 필요"
- 제보 0건 가게는 빈 상태 + 제보 유도
- **뒤로가기는 온 길로**(`router.back()`) — 여러 경로에서 진입하므로 고정 목적지를 박으면 엉뚱한 곳으로 나간다

결정 필요: 가게 사장님 반발 시 가게 단위 비공개 옵션을 둘지(구매 장소 공개와 동일 이슈)

#### 시장 단위 환산 🆕

정의: 시장에서 실제로 파는 단위(1단·1망·1박스·묶음)를 기준 단위로 환산해 비교 가능하게 만든다.

해결하는 문제: 46종의 기준 단위가 kg·g·개·포기로 갈리는데 화면이 kg를 고정 가정하고 있었다.
게다가 시장은 kg로 안 파는 경우가 많아 **환산 없이는 비교 자체가 불가능**하다. 실사용 최대 결함이었다.

프로세스:
1. 품목의 기준 단위에 맞는 시장 단위 후보를 제시(kg 품목: 1kg·1단·1망·1박스 / 개 품목: 1개·3개·1봉지 등)
2. 사용자가 파는 단위를 고르고 그 단위의 가격을 입력
3. 앱이 기준 단위로 환산하고 **환산 근거를 문구로 밝힌다**("1망 = 1.5kg으로 계산했어요")

화면 요소: 즉석 판단·제보 폼에서 단위 칩 + 환산 안내. 장바구니·담기 스테퍼도 품목 단위로 표기

결정 필요: 1단·1망의 환산 계수(지금은 단 0.8kg / 망 1.5kg 가정). 지역·품목마다 달라 실측 필요

#### 장보기 코스 🆕

정의: 장바구니를 기준으로 "한 곳에서 다 사기" vs "두 곳 돌기"의 금액을 비교해 보여준다.

해결하는 문제: 품목별 최저가를 알려주면 가게가 흩어져 발걸음이 늘어난다. 절약액과 **들르는 가게 수**를
같이 보여주지 않으면 "비용 절약"이 "노력 절약"을 잡아먹는다.

프로세스:
1. 가게별·품목별 최신 제보 단가를 색인(이상치 제외)
2. 한 곳 최선안 = 커버 품목이 많은 쪽 우선 → 같으면 총액이 싼 쪽
3. 두 곳 조합 전체를 계산해 최선안 도출
4. **두 곳이 실제로 더 싸지 않으면 제안하지 않는다**(괜히 발걸음만 늘린다)
5. 제보가 없는 품목은 공공 시세로 대체하고 몇 개가 대체됐는지 밝힌다

화면 요소: 1안에 "추천" 배지. 2안은 트레이드오프를 한 문장으로("한 곳보다 1,600원 더 아끼지만
가게를 한 곳 더 들러야 해요"). 가게별 제보가 없으면 코스 대신 제보 유도 문구

결정 필요: 이동 거리·시간을 실제로 계산해 넣을지(지금은 "가게 수"만으로 노력을 표현)

#### 홈 시세·전일 등락 표시 🆕

정의: 홈 그리드 각 칸에 오늘 시세와 어제 대비 등락(▲▼%)을 함께 보여준다.

해결하는 문제: 홈이 이모지 그리드뿐이라 **어느 야채를 볼지 정할 정보가 0**이었다. 하나씩 들어가 봐야 했다.

프로세스:
1. 서버에서 46종 기준선을 한 번에 조립
2. 주간 시리즈 마지막 두 점으로 전일 대비 계산. **0.5% 미만은 "어제와 같음"**(매일 ±10원에 화살표가 뒤집히면 신호가 아니라 노이즈다)
3. 화면에 필요한 값만 요약 DTO로 클라에 전달(시리즈 전체 약 2,200 포인트를 보내면 페이로드 과다)

화면 요소: 오르면 빨강·내리면 초록(사는 사람 기준). 화살표는 `aria-hidden`이고 스크린리더 문구를 따로 둠

결정 필요: 등락 기준을 전일로 둘지 주간 평균 대비로 둘지

#### 이번 달 사기 좋은 야채(제철 최저가) 🆕

정의: 12개월 평균 시리즈에서 **지금 달이 저점권(3위 이내)**인 품목만 골라 홈 상단에 보여준다.

해결하는 문제: "계절별로 뭐가 싼지" 알 방법이 없던 문제. 식물학적 제철이 아니라 **실시세 계산값**이다.

프로세스:
1. 품목별 연 월평균에서 현재 월의 싼 순위 계산
2. 3위 이내 + 연 최고가 대비 5% 이상 싼 품목만 채택(근거가 얇으면 "싸다"고 말하지 않는다)
3. 할인폭 큰 순으로 최대 6개, 가로 스크롤로 노출(홈 세로 길이를 늘리지 않는다)

화면 요소: "연 최고가보다 N%↓" + 근거 라벨("1년 시세 기준"). 해당 품목 없으면 섹션 자체 미노출

결정 필요: 월별 최저가 시기 기능과 계산 근거가 같아 통합할지

#### 온라인가 비교 (4채널로 확장)

정의: 컬리·쿠팡·G마켓·B마트 가격을 **채널 성격과 함께** 보여준다. 오프라인 판단의 보조 기준.

해결하는 문제: 시·도 단위 공공시세만으론 채널별 가격차를 못 보여주는 문제.

프로세스:
1. 채널별 가격을 기준 단위로 환산해 저장. 환산 불가 SKU는 엔트리를 두지 않는다(억지 환산이 더 위험)
2. 최저가 1줄로 요약해 **기본은 접어둔다** — 기획안 §3이 온라인 비교의 메인 기능화를 제외했다
3. 펼치면 채널별 가격 + 성격 라벨(새벽배송·당일배송·오픈마켓·즉시배송) + 단서(배송비 별도·회원가)

화면 요소:
- 채널 성격을 **반드시** 함께 표기. 성격을 숨기고 금액만 줄 세우면 "즉시배송이 제일 비싸다"는 당연한 결론만 반복돼 정보량이 0이 된다
- 실측이 아닌 값이 섞이면 "일부 예시" 라벨(현재 컬리만 실측, 나머지 3채널은 더미)
- 맨 아래에 "오프라인 동네 가격이 기준이고 온라인은 참고용" 명시

결정 필요:
- 크롤링 갱신 주기
- 실연결 방법 — 쿠팡은 봇 차단이 강하고 G마켓은 판매자 편차가 크고 B마트는 앱 전용이다. 채널별로 난이도가 달라 일괄 크롤링이 어렵다

#### 제보 신뢰 3종(신선도·교차검증·이상치) 🆕

정의: 제보 하나하나에 신뢰 신호를 붙여 "이거 믿을 수 있나"에 답한다.

해결하는 문제: 이웃 제보가가 유일한 차별점인데 **검증 장치가 0**이었다. 틀린 제보 하나가 서비스 전체 신뢰를 깎는다.

프로세스:
1. **신선도** — 오늘/어제/N일 전 표시. 1주일 넘으면 흐리게 + "오래됨" 경고(야채 가격은 주 단위로 움직여 낡은 제보는 오히려 해롭다)
2. **교차 검증** — 같은 가게·같은 품목 제보가 2건 이상이면 "이웃 N명 확인" 배지(1건은 근거가 얇고 2건 이상은 서로가 증인)
3. **이상치** — 시세의 3배 초과 또는 ⅓ 미만이면 목록 맨 아래로 내리고 "확인 필요" 표시. **지우지 않는다**(집계에서만 제외)

화면 요소: 시세 화면 제보 목록 · 가게 상세 품목 행 공통. 이상치는 반투명 처리

결정 필요: 이상치 배수(3배/⅓)가 적절한지. 오래됨 기준(7일)이 품목별로 달라야 하는지

#### 단골 가게 🆕

정의: 자주 가는 가게를 등록해두고 홈에서 "단골집 오늘 가격"을 먼저 본다.

해결하는 문제: 반복 구매가 타깃(4인 가족 장보기 담당)의 특성인데 매번 가게를 다시 찾는 건 노력 낭비다.

프로세스:
1. 가게 상세 앱바 북마크로 등록/해제(localStorage)
2. 홈에 단골집 요약 카드 — 품목 수, 최근 제보 시점, 시세 대비 평균

화면 요소: 단골이 없으면 **아무것도 그리지 않는다**(빈 카드로 홈을 늘리지 않는다).
아이콘 버튼이라 aria-label로 상태까지 말한다

결정 필요: 단골 개수 상한. 단골 가게 가격 변동 알림을 붙일지

#### 지난 장보기 그대로 담기 🆕

정의: 내 구매 이력을 **날짜(= 한 번의 장보기) 단위**로 묶어 장바구니에 그대로 복원한다.

해결하는 문제: 반복 구매가 많은데 매번 장바구니를 새로 채우는 건 시간·노력 절약과 반대다.

프로세스:
1. 구매 표시된 내 제보를 날짜별로 묶는다(사용자의 기억 단위가 "그날 장 본 것")
2. 최근 2회를 품목 목록 + 그날 총액과 함께 보여준다
3. 버튼 한 번으로 전 품목·수량 복원

화면 요소: 장바구니 빈 상태에 노출. 구매 이력 없으면 미노출

결정 필요: 몇 회분까지 보여줄지. 그날 가격도 함께 복원해 보여줄지

#### 재구매 주기(살 때 된 야채) 🆕

정의: 내 구매 간격에서 재구매 주기를 추정해 "그거 살 때 됐어요"를 홈에서 알려준다.

해결하는 문제: 매번 시세를 확인하러 앱을 켜야 하는 문제. 재방문 이유를 만든다.

프로세스:
1. 품목별 구매 날짜에서 **간격의 평균**을 주기로 계산
2. 이력이 1건뿐이면 근거가 없어 기본 14일을 쓴다(가정임을 문구로 밝힌다)
3. 주기를 넘긴 품목만, 많이 지난 순으로 최대 4개

화면 요소: "마지막 구매 N일 전 · 보통 M일마다 사셨어요" + 시세 보기.
살 때 된 품목이 없으면 섹션 미노출

결정 필요: 가격 알림 설정과 통합할지(둘 다 "다시 살 때를 알려준다"는 같은 목적)

#### 소비 요약·절약 계산

정의: 구매로 표시된 제보만 모아 그날 시세와 비교해 절약·초과 금액을 계산한다.

해결하는 문제: 사고 나서 잘 산 건지 모른다는 문제. 제보할 유인도 없다.

프로세스: 구매 표시 제보 조회 → 그날 대표 시세와 비교 → 절약·초과 계산 → 마이페이지 상단 고정

화면 요소: 구매 0건이면 "야채를 사고 가격을 제보하면 시세보다 얼마나 아꼈는지 알려드려요".
절약이면 초록, 초과면 주황

결정 필요: 절약액이 마이너스(초과)일 때 문구 톤

#### 온보딩(닉네임 + 동네)

정의: 첫 진입 시 닉네임과 동네(행정동)를 입력받아 이후 이웃으로 표시한다.

해결하는 문제: 제보할 유인이 없다는 문제. 소속감과 권위를 부여한다.

프로세스: 닉네임 입력 → GPS 자동 감지(동 단위) → 필요 시 수동 보정 → 웰컴 → 홈

화면 요소: GPS 거부 시 수동 선택. 동 단위로 검색·선택(구 단위는 "동네" 체감이 안 남)

결정 필요: 닉네임을 필수로 할지 선택으로 할지

#### 촬영 제보

정의: 사진을 찍어 제보하면 품목·양·가격을 프리필해 짧게 끝낸다.

해결하는 문제: 허위·장난 제보를 못 거르는 문제. 사진으로 신뢰도를 높인다.

프로세스: 카메라 열기(권한 거부 시 에러 상태) → 셔터로 프레임 고정 → 프리필 확인 → 구매 여부 → 제출

화면 요소: 카메라 권한 거부 시 대체 문구와 직접입력 유도. 진입 경로는 F03-1뿐

결정 필요: 실제 이미지 인식을 언제부터 붙일지(지금은 항상 감자로 인식되는 시뮬레이션)

#### 정확한 위치 찍기(GPS + Kakao 검색)

정의: GPS 좌표로 근처 청과물·마트를 찾아 제보 위치를 동보다 좁게 특정한다.

해결하는 문제: 구 단위로 받아도 동네 단위보다 넓어 문제가 안 풀리는 문제.

프로세스: GPS 확인 → Kakao 키워드 검색(반경 내 "청과"·"채소"·"과일") → 목록 선택, 미등록 시 직접 입력.
API 키 없으면 더미 가게 목록으로 폴백

화면 요소: 검색 결과 없으면 바로 직접 입력 폼으로 전환

결정 필요: 반경(m). Kakao 실연결 시점

#### 구매 장소 공개

정의: 제보 목록 각 행에 다녀온 가게명을 노출하고, 누르면 가게 상세로 보낸다.

해결하는 문제: 제보 목록만 봐서는 신뢰·소통이 생기지 않는 문제. **이번 라운드에서 가게 축의 입구가 됐다.**

프로세스: 제보 시 place 저장 → 목록 행에 가게명 표시 → 탭하면 F09

화면 요소: place 없는 제보는 가게명 생략

결정 필요: 가게 사장님 반발 시 비공개 옵션

#### 동네 댓글

정의: 시세 화면 하단에 같은 동 이웃끼리 댓글을 남긴다.

해결하는 문제: 제보가 일방향 데이터라 이웃 간 소통·신뢰가 안 쌓이는 문제.

프로세스: 같은 동·같은 품목 댓글 목록 확인 → 닉네임+내용 등록

화면 요소:
- **기본 접힘**(UX 3차 변경) — "지금 살까" 판단에 필요하지 않은 섹션이 판단 근거를 밀어내지 않게
- 댓글 없으면 "아직 댓글이 없어요"
- 입력은 seed TextField(이전엔 여기만 raw input이라 앱 안에 입력 필드가 두 종류였다)
- 한글 IME 조합 중 Enter 무시

결정 필요: 구매인증(실제로 산 사람만 댓글) 게이트를 둘지

#### 뱃지

정의: 제보·구매 건수가 기준을 넘으면 마이페이지에 단계별 뱃지를 표시한다.

해결하는 문제: 제보할 유인이 없다는 문제.

프로세스: 내 제보·구매 건수 집계 → 기준(1/5/15건 제보, 3건 구매) 통과 여부

화면 요소: 미획득 뱃지는 반투명으로 다음 목표를 알려줌

결정 필요: 종류·기준을 실사용 데이터로 재조정할지

#### 가격 알림 설정

정의: 찜한 야채마다 가격 알림을 켜고 끈다(실제 발송 없음, 예시 UI).

해결하는 문제: 매번 시세를 확인하러 앱을 켜야 하는 문제.

프로세스: 마이페이지에서 찜한 야채별 토글

화면 요소: 찜한 야채 없으면 안내 문구, 예시 기능임을 라벨로 명시.
**seed Switch로 교체**(직접 만든 토글이 존재하지 않는 토큰을 써서 ON 상태가 무색으로 보이던 버그 수정)

결정 필요: 실제 푸시 인프라(FCM 등) 도입 시점과 알림 기준(하락폭 %)

#### 월별 최저가 시기

정의: 12개월 평균 시리즈에서 가장 쌌던 달을 계산해 시세 화면에 표시한다.

해결하는 문제: "언제 사는 게 싼지" 판단할 근거가 없는 문제.

프로세스: 연 시리즈 최저가 달 계산 → 최신 달 대비 % 차이 → KAMIS 미연결이면 "예시" 라벨

화면 요소: 최저가가 최신 달보다 안 싸면 배지 자체를 숨김

결정 필요: 식물학적 제철 데이터를 병기할지. "이번 달 사기 좋은 야채"와 통합할지

#### 랭킹(싼 가게 · 최저가 품목 · 제보왕)

정의: 동 단위로 세 가지 순위를 보여준다.

해결하는 문제: 시세 화면만 봐서는 앱을 계속 켜볼 이유가 약한 문제.

프로세스:
1. 탭 전환 — **"싼 가게"가 첫 탭**(UX 변경). 사용자의 질문은 "무엇이 싼가"보다 "어디로 갈까"이고, 품목별 최저가만 주면 가게가 흩어진다
2. 싼 가게 = 시세 대비 평균이 싼 순 → 같으면 제보가 많은 순(근거가 두꺼운 쪽)
3. 최저가 품목·제보왕은 예시 데이터

화면 요소: 싼 가게 탭은 **실제 제보 집계**(예시 아님)이고 나머지 두 탭은 "예시 데이터입니다" 명시.
가게별 제보 없으면 빈 상태 + 제보 유도. seed SegmentedControl 사용

결정 필요: 실서비스 전환 시 집계 주기(실시간/일배치)

#### 장바구니(장보기 전 예산 계획)

정의: 살 품목+수량을 담아 예상 총액을 비교하고 장보기 코스를 제안한다.

해결하는 문제: 품목 화면을 하나씩만 보면 "오늘 장보기 전체 예산"을 가늠하기 어려운 문제.

프로세스:
1. 시세 화면 또는 장바구니 자체(바텀시트·찜 퀵애드·지난 장보기 복원)에서 담기
2. 수량 조절·삭제 — 단위는 품목별
3. **"공공 시세 기준"과 "동네 최저가를 전부 모으면"을 구분**해 보여준다(UX 변경). 동네 최저가 합계는 가게가 흩어져 한 번에 살 수 없는 이론값이다
4. 실현 가능한 안은 장보기 코스가 담당
5. 각 행 "제보하러 가기"로 제보 플로우 연결

화면 요소:
- 빈 상태 "아직 담은 야채가 없어요" + 찜 퀵애드 + 지난 장보기 복원
- 최대 절약 가능액 아래 "가게가 흩어져 있을 수 있어요" 단서
- 삭제 경로를 **하나로 정리**(이전엔 1kg에서 −를 눌러도 삭제돼 경로가 둘로 갈렸다)

결정 필요: 구매 확정(체크아웃)을 추가할지, 계획 전용으로 남길지

#### 카드뉴스(가격 등락 요약)

정의: 홈에서 "요즘 이 야채 싸요/비싸요"를 수동적으로 알려주는 콘텐츠.

해결하는 문제: 그래프는 능동적으로 눌러봐야 보인다는 문제.

프로세스: 홈 티저 노출 → 카드뉴스 화면

화면 요소: 전부 예시/더미 라벨

결정 필요: 콘텐츠를 사람이 쓸지 시세 계산으로 자동 생성할지

## UX 검토 3회에서 고친 것

**1회차 — 플로우 파손·데이터 정합성**
- 장바구니·담기 수량이 kg 고정 표기 → 품목 단위로 분기(**오이 3개가 "3kg"으로 보이던 버그**)
- 가게 상세·즉석 판단의 뒤로가기가 고정 목적지라 엉뚱한 곳으로 나감 → `router.back()`
- 즉석 판단 하단 CTA가 조건부로 나타나 판정 순간 화면이 튐 → 항상 렌더 + 비활성
- 홈 46종 그리드가 16줄로 홈을 지배 → 그룹 칩 7종

**2회차 — 컴포넌트를 seed 디자인 시스템으로 재설계**
- 세그먼트 탭 3곳(랭킹·마이페이지·제보 폼 구매 여부) 복붙 → seed `SegmentedControl`
- 직접 만든 가격 알림 토글 → seed `Switch` (**ON 배경이 존재하지 않는 토큰이라 무색이던 버그** 발견·수정)
- 댓글 raw `<input>` → seed `TextField` (앱 안에 입력 필드가 두 종류였다)
- GNB 텍스트+6px 점 → 아이콘(채운/선) + 색 + `aria-current` 3중 신호
- raw hex/arbitrary px 정리 — report-list 15→0, 시세 화면 12→0, 그래프 10→0
- 반복 마크업을 공통 컴포넌트로 추출: `VegetableThumb`(이모지 폴백) · `QuantityStepper` · `TrendLabel` · `FreshnessTag` · `CollapsibleSection`

**3회차 — 정보 위계·상태 3종·접근성**
- F03 8블록이 같은 무게 → **동네 제보가를 그래프 위로**, 레시피·댓글은 기본 접힘, 담기·판단 액션을 한 묶음으로
- 로딩 화면 없음 → `loading.tsx`(폰 프레임 유지해 전환 시 레이아웃 안 튀게)
- 에러 화면 없음 → `error.tsx`(사과문·기술용어 없이 무엇이 안 됐는지 + 지금 할 수 있는 것)
- 색·기호만으로 뜻을 전하던 곳에 스크린리더 문구 추가(등락 화살표·신호등 판정·아이콘 버튼)
- 터치 타겟 44px 유지(스테퍼·GNB·접기 버튼)

## 아키텍처 결정 (백엔드·프론트 공용)

**시세 기준은 항상 서버에서 내려준다.**
제보는 localStorage(클라)에 있어 목록은 클라에서 만들지만, 비교 기준(공공 시세)까지 클라에서
더미로 계산하면 KAMIS 연결 시 서버 화면과 숫자가 어긋난다. → `getPriceMap()`으로 품목→시세 맵을
서버에서 내려 랭킹·장바구니·가게 상세·즉석 판단이 같은 기준을 쓴다.

**이웃 제보 시드는 동네별 지연 생성.**
46종 × 100여 개 동을 미리 만들면 1만 건이 넘어 렌더마다 정렬 비용이 커진다 → 요청된 동네만 생성·캐시.

**홈은 46종 기준선을 서버에서 한 번에 조립하고 요약 DTO만 클라로 보낸다.**
시리즈 전체(약 2,200 포인트)를 보내면 페이로드가 과하다.

## 결정 필요 모음 (우선순위)

1. **46종 등급 코드 최종 검증** — 틀리면 KAMIS가 품목별로 조용히 빈 값을 반환한다 (최우선)
2. **배추·무 계절 품종 kindCode 4개 실제 값** — 규격 문서에 없음
3. **시장 단위 환산 계수**(1단·1망) 실측 — 환산이 틀리면 판정 전체가 틀린다
4. 방울토마토 단위가 "개"인지 팩인지
5. 신호등 ±8% 밴드, 이상치 3배/⅓, 오래됨 7일 — 실사용 재조정
6. 온라인 3채널(쿠팡·G마켓·B마트) 실연결 방법과 갱신 주기
7. 허위 제보 신고·제재 기준 / 가게 비공개 옵션
8. 가격 알림 실제 발송 인프라
9. **예시 데이터 노출 범위** — 지금 예시 라벨이 붙은 곳이 랭킹 2탭·카드뉴스·레시피·가격알림·온라인 3채널이다. UT 참가자가 "미완성"으로 인식해 정작 이웃 제보가 반응이 흐려질 위험이 있다
