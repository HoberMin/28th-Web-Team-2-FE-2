# 로그인 연동 — 백엔드 확인 요청

> 작성 2026-08-18 · 프론트(Next.js)
> 기준: `https://api.marketgo.kro.kr/v3/api-docs` (2026-08-18 조회) + 전달받은 `kakao_login.md`

**A만 답 주시면 프론트는 진행합니다.** B·C는 나중에 주셔도 되고, C는 저희가 직접 호출해서 확인할 수 있는 것들이라 참고용으로만 적었습니다.

> 프론트 진행 상황(2026-08-18): API 레이어와 토큰 갱신(`proxy.ts`)은 이미 붙여 뒀습니다.

## A. 만들어주셔야 진행되는 것 (2건)

### 1. 로그인한 사용자를 조회하는 API가 필요합니다

**무엇이 없나**
`PATCH /api/v1/users/me`(닉네임 저장)는 있는데 **읽는 API가 없습니다.**

**왜 필요한가**
- 마이페이지에 **내 닉네임을 표시할 수 없습니다.**
- 재방문 시 **온보딩(닉네임→동네)을 이미 마친 사람인지 판단할 수 없습니다.** 지금은 로그인 응답이 `{ accessToken }`뿐이라 신규/기존 구분 수단이 아예 없습니다.
- 프론트에 자체 플래그를 저장하는 우회는 가능하지만, **기기·브라우저를 바꾸면 이미 가입한 분에게 온보딩이 다시 뜹니다.** 서버가 알려주는 것 말고는 정확한 방법이 없습니다.
- 토큰이 아직 살아 있는지 확인하는 용도로도 씁니다. 지금은 보호된 API를 아무거나 찔러보는 것 외에 세션 유효성을 볼 방법이 없습니다.

**이렇게 답해주시면 됩니다**
```
1. GET /api/v1/users/me — 추가 예정 / 이미 있음(경로: ___) / 어려움
   응답 예시:
     { "nickname": "홍길동", "regionId": "1121510100" }
   닉네임 미설정 상태의 응답은? (null / 빈 문자열 / 404)
```

> **대안**: 이 API가 어려우시면 **로그인 응답에 `isNew` 같은 필드**만 넣어주셔도 온보딩 분기는 해결됩니다.
> 단 닉네임 표시는 여전히 못 합니다. **둘 다 만들 필요는 없습니다** — 판단 기준이 두 개가 되면 나중에 어긋나니 한쪽으로 정해주세요.

---

### 2. 카카오 앱에 저희 배포 도메인을 등록해주세요

**무엇이 필요한가**
- 카카오 개발자 콘솔 → **플랫폼 / Redirect URI**에 프론트 배포 주소 등록
- 저희가 써야 할 **앱 키**가 무엇인지 (JavaScript 키 / REST API 키 중)

**왜 물어보는가**
카카오 앱을 어느 쪽이 관리하는지 모릅니다. 백엔드가 `idToken`을 검증하고 있으니 **백엔드가 만든 앱일 가능성이 높고**, 그렇다면 저희가 콘솔에 접근할 수 없어 등록을 부탁드려야 합니다. 저희가 관리하는 앱이면 직접 하겠습니다.

또 **백엔드가 검증하는 앱과 프론트가 로그인하는 앱이 같아야 합니다.** 다르면 audience가 안 맞아 검증에서 떨어집니다.

**이렇게 답해주시면 됩니다**
```
2. 카카오 앱 관리 주체: 백엔드 / 프론트 / 공용
   - 저희가 쓸 앱 키: (JS 키 / REST 키)
   - Redirect URI 등록 필요 여부: (필요하면 저희가 주소 전달드립니다)
```

## B. 정책 결정이 필요한 것 (1건)

### 3. 비회원은 어디까지 쓸 수 있나요?

**지금 스펙이 애매합니다**
`GET /api/v1/items`·`GET /api/v1/stores/nearby`는 **인증 설정이 없는데** 응답에 `isLiked`(찜 여부)가 있고, 쿼리에 `favoriteOnly`·`onlyLiked`가 있으며 `401`도 선언돼 있습니다. **로그인 여부에 따라 같은 API가 다르게 동작한다**는 뜻으로 읽힙니다.

**왜 물어야만 알 수 있나**
토큰 없이 호출해보면 *현재 동작*은 알 수 있지만, **그게 의도한 정책인지는 알 수 없습니다.** 그리고 이게 정해지지 않으면 **캐싱 전략을 못 짭니다** — 비회원 응답은 모두에게 같으니 캐시해도 되지만, 회원별로 다른 응답을 캐시하면 **다른 사람의 찜 상태가 보이는 사고**가 납니다. 저희 쪽에서 가장 조심하는 부분입니다.

**이렇게 답해주시면 됩니다**
```
3. 비회원에게 막을 기능: 찜 / 제보 / 댓글 / (그 외)
   토큰 없이 /items 호출 시 의도한 동작: 200(isLiked 전부 false) / 401
   토큰 없이 favoriteOnly=true 호출 시: 빈 목록 / 400 / 401
```

## C. 저희가 직접 확인할 것 (답변 불필요 — 공유용)

아래는 호출해보면 알 수 있는 것들이라 **묻지 않고 실측으로 진행합니다.** 다만 스펙 문서와 실제가 다른 지점이라 알아두시면 좋겠습니다. 이미 아시는 내용이면 알려주시면 저희 시간이 줄어듭니다.

| 항목 | 상태 | 저희 처리 |
|---|---|---|
| **로그인 경로가 3곳에서 다름** — 문서 상단 `api/v1/auth/kakao/login` / 문서 본문 `/api/auth/kakao/login` / Swagger `/api/auth/{providerType}/login` | Swagger에 `v1`이 없음 | Swagger 기준으로 호출해보고 맞추겠습니다 |
| **로그아웃 스펙 불일치** — 문서는 `Bearer 필요 / 204`, Swagger는 `인증 설정 없음 / 200` | — | 호출해서 확인 |
| **토큰 만료 시간** | 문서에 없음 | accessToken은 JWT `exp`를 디코드하면 알 수 있어 저희가 확인합니다. **refreshToken 회전 여부(재발급 시 새로 내려오는지)만** 알면 좋겠습니다 |
| **에러 응답 형식을 알 수 없음** — 400·401·404·502가 전부 성공 스키마를 재사용 | Swagger 생성 이슈로 보임 | 상태 코드로만 분기하고 본문은 신뢰하지 않습니다 |
| **`Set-Cookie`가 Swagger에 없음** — refreshToken을 *받는* API는 있는데 *주는* 곳이 스펙에 없음 | 문서에만 있음 | 문서 기준으로 구현 |
| **쿼리 파라미터가 `request`로 나옴** — `/regions/search`·`/regions/nearby`·`/kamis/daily-prices` | Swagger를 그대로 읽으면 `?request=`를 만들어 400. 실제로는 `?keyword=` 형태 | 확인 완료, 저희 문서에 메모함 |
| **`regionId` 타입 불일치** — `SearchResult`는 `string("0111010100")`, `NearbyRegionResponse`는 `int64` | 숫자로 다루면 **앞자리 0이 사라짐** | 프론트는 문자열로 통일. **가능하시면 서버도 문자열로 통일 부탁드립니다** |
| **응답 감싸는 방식이 엔드포인트마다 다름** — `/regions/search`만 `{code,message,data}`, 나머지는 그대로 또는 배열 | — | 엔드포인트마다 따로 처리. **통일 계획 있으면 알려주세요** |
| `servers`가 `http://`, `info.title`이 `Demo API` | Swagger 기본값 | `https`로 호출 중 |

## 참고 — 프론트 구현 방식 (답변 불필요)

전달주신 `kakao_login.md` 2장은 **브라우저가 백엔드를 직접 호출하는 방식**을 전제로 「accessToken은 메모리에 보관」·「`credentials: 'include'`」·「401 받으면 재발급 후 재시도」를 안내하고 있습니다.

저희는 **서버 렌더링 + BFF 구조**라 브라우저 대신 **Next.js 서버가 백엔드를 호출**합니다. 브라우저 메모리의 토큰은 서버가 읽을 수 없어 그 방식을 쓸 수 없고, 대신 토큰을 저희 서버에서 보관해 `Authorization` 헤더로 붙입니다. refreshToken 쿠키도 저희 서버가 헤더로 직접 중계합니다.

**백엔드는 바꾸실 게 없습니다.** 서버 입장에서 헤더가 오는 건 동일합니다.

한 가지만 참고로: 프론트 도메인과 API 도메인이 다르면 `SameSite=Lax` 쿠키는 브라우저 fetch에 실리지 않아서, 문서대로 **브라우저에서 재발급을 호출하는 방식은 동작하지 않습니다.** 저희 구조에서는 문제가 안 되지만, 나중에 앱 등 다른 클라이언트가 붙을 때 같은 문제가 생길 수 있습니다.
